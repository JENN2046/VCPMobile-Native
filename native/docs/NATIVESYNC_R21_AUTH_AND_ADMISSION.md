# NativeSync R2.1: native auth and admission map

This is source-grounded design, not a validated native HTTP client or a claim of installed R2.1. Source: original verified NativeSync R2.1 installation ZIP, cumulative ToolBox patch SHA256 62e983d25e42a6318140797cc42f14e48800bcd2ff71c36f824f8245041aac13; public base e84d51aa8a34de5ceb863c430b1ce480f6356054 at Plugin/NativeSync/mobile/portal.js (base blob 67bd37ffafa672a98abb6d405c777c236aa80193) and unchanged mobile/connection.js (blob 62cee3d30aa9a9b5b5c699b367b35bb55e818f38). Portal patch declares after blob 6950b91ca70b4f161906e28036b9ccec589e73a5; an independently recomputed complete after-blob remains future verification.

The existing portal is at /mobile on an HTTPS VCPToolBox host. All /mobile/api requests require HTTPS. POST requests must include Origin exactly equal to configured NativeMobileOrigin, even from a native HTTP client; Origin mismatch is 403 ORIGIN_REJECTED. Do not redirect authenticated submissions across hosts or connect directly to internal NativeSync push/pull.

POST /mobile/api/pair with one-time {code} issued by trusted existing pairing mints an HttpOnly, Secure, SameSite=Strict cookie named __Secure-vcp_mobile and Path=/mobile. The cookie is the session credential; store it in isolated platform-protected HTTP storage, never in the SQLite recovery journal or logs. Session revocation is a server request, POST /mobile/api/connection/disconnect. Connection/authenticate consumes serverUrl and apiKey only in the explicitly configured host workflow; do not assume a reusable desktop API key or synthesize one.

GET /mobile/api/session after cookie authentication returns allowed Topics and recovery: {version:1,entryId,sessionMarker} (accepted patch). Unauthorized -> PAIR_REQUIRED 401. POST /mobile/api/conversations/:key/messages allows requestId/text/attachments; .../invitations allows requestId/agentId. Both require cookie + Origin + Topic scope. Set X-NativeSync-Entry-Id and X-NativeSync-Session-Marker from the current recovery context; stale supplied guards -> SUBMISSION_CONTEXT_CHANGED 409, but those non-credential guards do not confer authority. GET /mobile/api/conversations/:key?after=<cursor> has paged history and an execution projection, not task-ownership rights or AA completion.

Application ordering: authorized session/Topic -> exact payload recovery validation -> per-entry/Topic SQLite admission -> persist attempted state BEFORE network send -> cookie/Origin/context-guarded POST -> on absent acknowledgement query authorized execution list and match original receipt/hash/kind/session -> clear local pending only on verified server acceptance. Never mint a new request ID to bypass unknown, and never auto-submit an old request from another session. Same-session retry must remain explicit. New prepare_topic_exclusive performs only local atomic admission; actual network, pairing and fault injection remain M2 work.

No production credentials, real messages, or private archive copied to this repository.
